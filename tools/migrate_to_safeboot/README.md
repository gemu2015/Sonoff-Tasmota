# migrate_to_safeboot — OTA migration from 2-app-OTA to safeboot layout

Purpose-built single-shot firmware that converts an ESP32 device with the
historic Tasmota 2-app-OTA partition layout to the modern safeboot layout
**without serial access** — useful for devices that were flashed years
ago, are physically unreachable, and where you want the ~1 MB of
filesystem space the new layout frees up.

The migrator is delivered like any normal OTA upgrade: build the `.bin`,
upload it via Tasmota's `Firmware Upgrade` page, the device reboots into
the migrator, the migrator confirms readiness via a tiny web UI, you
click **Migrate**, and the device flashes the new partition table +
safeboot binary in one shot, then reboots into safeboot for you to OTA
your real firmware.

## When to use this

Use it when **all** of these are true:

- Device is on the historic 4 MB 2-app-OTA layout (typically
  `partitions/esp32_partition_app1856k_fs1344k.csv` or similar — two
  ~1.9 MB app slots and a small spiffs).
- You want the larger filesystem the safeboot layout enables (≈ 1 MB
  more on a 4 MB device).
- The device is **not** physically reachable for serial flashing in the
  near term — otherwise just do a serial reflash, it's safer.
- The device's power is reasonably stable. The bricking window is one
  4 KB sector erase + one 4 KB write at offset 0x8000 (≈ 100 ms) where
  power loss = unrecoverable without a serial cable.

Don't use it if:

- The device has > 4 MB flash. The safeboot scheme matters less there;
  the marginal FS gain probably isn't worth the brick risk.
- You can reach the device. A serial reflash with a fresh
  `.factory.bin` is a 5-minute operation with no chance of bricking.

## What it does, in order

1. Boot up, connect to Wi-Fi using the existing Tasmota credentials
   stored in NVS (or fall back to a SoftAP named `safeboot-migrate-XXXX`).
2. Run a one-page web UI at `http://<device>/`. The page shows:
   - The currently-detected partition layout (read from 0x8000).
   - The size and CRC32 of the embedded `safeboot.bin` blob.
   - A **Migrate** button (POST to `/go`).
3. When you click **Migrate**, in this exact order:
   1. **Pre-flight**: re-read partition table @ 0x8000, confirm the
      device really is on the old 2-app layout. Confirm the embedded
      safeboot blob's CRC matches the expected value baked in at build
      time.
   2. **Write safeboot**: erase the range 0x10000 .. (0x10000 + safeboot
      size, sector-aligned), then write the embedded safeboot blob to
      0x10000. This region is the OLD `app0` slot — the running
      migrator lives in OLD `app1` at 0x1F0000, so we're not writing
      under our own feet.
   3. **Verify safeboot**: read the just-written region back, recompute
      CRC32, compare. If mismatch, abort. Partition table is still
      old layout → device boots back into old app1 (the migrator) on
      next reboot. Try again. Safe.
   4. **Atomic-ish swap**: erase sector at 0x8000, write the new
      partition table (4 KB). **This is the brick window.** If power
      fails between erase and write, the partition table is gone and
      the bootloader can't find an app on next boot.
   5. **Update otadata** (sector at 0xE000): write a clean otadata that
      designates the safeboot partition as the boot target.
   6. **Reboot.**
4. The device boots into the new layout: bootloader → safeboot →
   safeboot's WebUI offers OTA upload of the real firmware.
5. You upload your normal Tasmota firmware (built for the safeboot
   layout) via safeboot's WebUI. Done.

## Files

| | |
|---|---|
| `migrate_to_safeboot.ino` | main sketch — Wi-Fi, web UI, migration |
| `partitions_old.csv` | reference: the old layout the migrator EXPECTS to find |
| `partitions_new.csv` | the new safeboot layout to be written at 0x8000 |
| `embedded/build_blobs.sh` | regenerates the embedded `.h` blobs from a fresh `safeboot.bin` |
| `embedded/safeboot_blob.h` | safeboot bytes + expected CRC, generated by the script |
| `embedded/partitions_blob.h` | new partition table bytes + CRC, generated |
| `platformio.ini` | build config; partitions = `partitions_old.csv` so the binary fits the old `app1` |

## Build

The safeboot binary is **not** built here — Tasmota ships pre-built ones,
chip-specific, at `variants/tasmota/<chip>-safeboot.bin`. Pick the one
matching your target:

| chip variant      | source file                                    |
|-------------------|------------------------------------------------|
| ESP32 D0WD        | `variants/tasmota/tasmota32-safeboot.bin`      |
| ESP32-C3          | `variants/tasmota/tasmota32c3-safeboot.bin`    |
| ESP32-C6          | `variants/tasmota/tasmota32c6-safeboot.bin`    |
| ESP32-S3          | `variants/tasmota/tasmota32s3-safeboot.bin`    |

(`pio-tools/post_esp32.py` auto-fetches missing variants from
`http://ota.tasmota.com/tasmota32/release/`. If yours isn't in the repo
yet, run any normal Tasmota ESP32 build once and it'll appear.)

Then:

```sh
# 1. Generate the embedded blob headers — picks safeboot for your chip.
#    Default is tasmota32 (generic ESP32 D0WD, e.g. WT32-ETH01).
cd tools/migrate_to_safeboot/embedded
./build_blobs.sh                       # ESP32 D0WD
# CHIP=tasmota32s3   ./build_blobs.sh   # for an ESP32-S3 target
# CHIP=tasmota32c3   ./build_blobs.sh   # for an ESP32-C3 target

# 2. Build the migrator firmware
pio run -d tools/migrate_to_safeboot
```

The output at `tools/migrate_to_safeboot/.pio/build/migrator/firmware.bin`
is ≤ 1.9 MB and OTAs cleanly into the old `app1` slot.

## Workflow recommendation

1. **Test on a sacrificial reachable device first.** Even if you've
   audited the code, run it on a board you can recover via serial.
   Catch any flash-layout / chip-variant surprises there.
2. **Migrate one production device at a time.** If a brick happens,
   you don't lose the whole fleet at once.
3. **Do the migration during a stable power window.** UPS or battery
   backup if you have it.
4. **Keep a serial cable handy.** If the migration fails mid-write
   (the 4 KB sector window), you'll need to physically reflash that
   one device.

## Limitations / known sharp edges

- **No rollback after step 4.** Once the partition table is written,
  the device commits to the new layout. If safeboot itself somehow
  fails to boot (corrupted blob, wrong chip variant), serial reflash
  is the only recovery.
- **NVS data is preserved.** The NVS partition (Wi-Fi creds, hostname,
  etc.) sits at the same offset in both layouts so it survives.
- **Settings file is NOT preserved.** Tasmota settings live in the
  filesystem partition, which moves and shrinks/grows. Plan to
  re-configure after migration, or back up `Settings.json` first via
  the Tasmota web UI.
- **Single chip variant per build.** The embedded safeboot blob is
  chip-specific. Build separate migrators for ESP32-D0WD, ESP32-S3,
  ESP32-C3 etc. — they're not interchangeable.
- **Not yet released as a Tasmota tool.** This is a sketch. Audit it,
  test it, and own the risk.
